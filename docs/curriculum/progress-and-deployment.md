# Versioned lesson progress and deployment

The browser persists stage, responses, visited activities and completion under
`syntutor:lessons:v1:<identity>`, with one `<lesson_id>@<content_version>` record.
Guests use a device-local identity; account IDs have separate device caches.
Old versions remain historical and never automatically complete a new version.
Local lesson XP is derived from unique completed version keys, not incremented
on replay. Guest/offline caches are learning aids, not trusted leaderboard data.

The UI saves after an answer/navigation/stage transition and shows account sync
state. Network failure retains the device cache and offers retry. Account requests have a five-second bound; after a failure, later activities remain local until an explicit retry, so an outage cannot stall every lesson action. A storage
failure retains the in-memory session and clearly reports that persistence is
unavailable. Signing out/changing account discards the active in-memory view;
a late response cannot replace the new identity's store.

## Account database contract

Prepared migrations, in order:

1. `20261108000000_versioned_lessons.sql`: private RLS progress/award tables,
   server-owned catalog and `save_lesson_progress` RPC.
2. `20261108000001_lesson_catalog.sql`: reviewed lesson/version/prerequisite and
   answer contract. Generated by `scripts/seed_lessons.py`, checked for drift.

The RPC derives the user from the verified JWT `sub`, validates answers against
the server-owned versioned catalog and checks prerequisites and all activities.
It accepts neither caller identity nor XP. The transaction serializes the user's
lesson writes, inserts a unique `lesson:<id>:<version>` award event, and adds 15
XP only on the first insert. Correct answers/completions survive stale replays.
Direct progress/award writes are denied; read access is own-identity only.
The existing level curve is preserved until M7. Existing global legacy XP write
policies/leaderboard privacy are not certified by this isolated M4 path.

The SQL is tested in a fresh PGlite PostgreSQL engine with mocked request JWT
claims. This exercises actual SQL, PL/pgSQL, permissions and RLS rather than a
JavaScript simulation. Repeated concurrent submissions share that engine's
single connection; no hosted multi-connection load test is claimed.

**Hosted status:** these migrations have not been applied to the linked
production Supabase database. No production credentials/database connection was
available for this task. Account/device-local progress works without them;
cloud sync and trusted shared player XP require the two prepared migrations to
be deployed through the project's normal migration process. The UI reports the
pending/unavailable sync instead of claiming a cloud save. No live user-data
backfill or destructive migration has been performed.

For a later lesson change, add a new content version and matching reviewed seed;
never change an existing published answer key in place. Keep previous catalog
versions so old progress remains interpretable.

Rollback the frontend PR to restore the prior entry point. For a database
rollback, disable the new RPC execution grants and keep the new tables/award
records for recovery; do not subtract or drop already recorded XP blindly.
These additions do not require deleting or rewriting legacy quiz/history data.

Security basis: [Supabase database functions](https://supabase.com/docs/guides/database/functions),
[Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security),
and [Clerk's Supabase integration](https://clerk.com/docs/guides/development/integrations/databases/supabase).
`SECURITY DEFINER` uses an empty search path with schema-qualified references;
execute grants are explicit and JWT identity is required inside the RPC.
